# 流量、连接数、限速与动态切换实测记录

日期：2026-11-16。基线：面板 2.3.300、Agent 2.2.212、FXP 2.2.122（提交 `3a264f35`）。修复在本地工作区完成，测试 Agent 仅部署到隔离容器，不代表已发布。

## 范围与方法

在一台 Debian 13 / Linux 6.12 云主机内建立隔离 Docker 网络，分别运行面板、三个节点、客户端与目标服务。请求经过真实 Agent、转发运行时及内核。没有修改宿主生产转发服务。

共 28 条路径：iptables、nftables、Realm、Socat、GOST、Nginx 六种普通转发；V1、V2、V3 TLS/WS/HTTP；GOST TLS/WSS/TCP 及复用模式；Nginx 隧道；三节点 V1/V2/V3/GOST TLS；六种工具的三节点转发链。使用自建双向 TCP 与 UDP 回传发生器核对客户端、目标、规则累计、历史入库与用户扣量。

这是同一物理机的多个网络命名空间测试，不能代替跨公网、多宿主、丢包、MTU、NAT、防火墙和 Mimic 环境的验证。限速结果按十进制 Mbps 解释；主机界面速率为 B/s。

## 已确认的问题与修复

### nftables 上传计数只覆盖连接首包

旧面板把上传计数放在 NAT prerouting，连接建立后的包不再经过 NAT 规则，因此一次约 20 MB 上传仅统计到 60 字节。普通转发与转发链均可复现。

将上传计数移至 forward hook，用 conntrack 原始目的端口区分共用目标的入口。修复后，对 TCP、64 并发 TCP、1200 字节 UDP、64 字节 UDP 四类负载复测：

| 路径 | 实际上传字节 | 入账上传字节 | 实际下载字节 | 入账下载字节 |
| --- | ---: | ---: | ---: | ---: |
| 普通 nftables | 33,057,560 | 33,397,540 | 61,056,000 | 61,475,260 |
| 三节点 nftables 链 | 33,057,560 | 33,402,836 | 61,056,000 | 61,416,796 |

修复后的差值为包头和 TCP 控制包等内核计数开销；规则累计、历史及用户扣量一致。已有规则更新面板后需重新同步应用，历史漏计无法恢复。

### Nginx 与共享 FXP 组交接

已复现 Nginx 隧道切换到已有 V1 共享组时长时间不通：原组成员提前启动完整新组，占用组锁等待旧 Nginx 端口释放，而切换规则的交接任务也需要该组锁。补齐同组成员对旧共享运行时的依赖，使端口交接先于整组启动；失败结果同样阻止组内成员抢先启动，无关组继续独立执行。

另一个切入方向也已复现：先让 Socat 正常转发，停 Agent 并删除该端口的本地状态文件，保留 Socat 服务，再修改为 Nginx 并启动 Agent。旧顺序先同步 Nginx，端口绑定失败后回滚，后续规则又等待同步结果，实测 TCP 拒绝连接、UDP 无回包。修复将未就绪的共享监听对应的残留清理提前为交接任务；本地标记缺失时也检查实际共享运行时归属。按同样步骤重测后 TCP/UDP 均完整传输。

修复后完成 24 次工具/隧道切换，涵盖五种普通工具、V1/V2/V3 单跳及三节点路径、GOST TLS 与 Nginx 普通转发之间的双向切换；每次核对实际标记并验证 TCP/UDP，全部成功。随后“Nginx 隧道 ↔ 已有三节点 V1”连续往返三轮，再切三节点 V2、V3、Socat、V1，共 10 次均通过 TCP/UDP 实测。

同时修复就绪判断：共享运行时配置回滚后，仅检查旧配置已有监听会误判新配置已应用。现在还需核对受管配置文件与期望内容一致，使失败的新配置继续重试。回归测试覆盖新配置应用、回滚及拒绝采用旧配置。

## 流量与扣量

- 成功传输的 V1/V2/V3 各模式及多跳路径，原生流量与业务字节一致。
- TCP、UDP、并发、小包各阶段的规则累计与历史入库一致；账户扣量等于接受入账统计之和。转发链仅选定一个节点计费，没有把整链各节点重复相加。
- 内核计数包含 IP/TCP/UDP 包头、ACK 及重传。1200 字节 IPv4 UDP 的包头占比约 2.3333%；64 字节 UDP 加 28 字节包头后高出 43.75%。
- GOST 的部分隧道在出口承载监听器计量，包含封装。小包放大封装占比，不能仅凭相对业务字节偏高判定重复计费。
- 普通上报约 30 秒合批，叠加采样与重试延迟。45 秒等待有时不足，后续快照能够观察到尾部数据入库；比较用量时需要等待结算稳定。
- 初轮 Nginx 隧道与 Nginx 链 TCP 未就绪，运行时就绪后重测均成功。高发包率下部分路径有丢包，需区分目标实际收到的字节与客户端发送字节。

报告失败重试验证：对测试入口到面板的报告暂时阻断，业务保持传输。恢复后 10 MB / 20 MB TCP 负载入账 10,013,980 / 20,023,720 字节；重放同一持久化待报批次并重启 Agent，累计增量为 0 / 0，未重复扣量。随后重启继续传输仍正常入账。

## 主机实时速率与连接数

三节点 V1 持续 40 秒、上传 1,000,000 B/s，27 次采样中各节点约 1.009–1.014 MB/s，符合包头开销；停止后回落至约 1–3 KB/s 的管理背景流量。主机累计增量与 Agent 原始网卡累计增量一致。顶部汇总会累加各节点各自的网卡流量，不能与单份业务扣量对等比较。

IPv4/IPv6 合计创建 32 对 TCP、两个监听套接字、16 个 UDP 套接字。41 次采样中稳定负载的 TCP inUse 从 28 增至 94、UDP 从 47 增至 63，与节点 /proc 一致，关闭后回落。缓存与心跳带来数秒延迟。主机 TCP inUse 包含监听器，不等于已建立业务连接数。

规则累计连接次数是另一口径：GOST 非复用承载可能包括探测连接，复用模式则以少量物理承载承接多个业务流；不能把它直接当作客户端或在线人数。

## 限速与连接数限制

限速按规则独立计算。用户、隧道、转发组和规则自身配置的正数上限分别作为该规则的上限约束，最终取其中最小值；不同规则不会共用一个带宽桶。因此同一入口主机上的两条 20 Mbps 规则可以分别达到约 20 Mbps，上下行分别计算。

Agent 侧保留了每条规则的限速作用域，并补齐了 FXP 入口规则在运行状态已存在时的配置刷新。取消 Guard 限速时会保留现有监听并切换为无限桶，减少在途连接被重启打断。多跳 V2 的 mimic 端口分配也调整为先取得数据库事务上下文，避免编辑事务与心跳分配互相等待。

连接数限制由入口 Agent 的独立 nftables 表执行。同一用户在一台入口主机上的普通转发、隧道、转发链、TCP/UDP 及 IPv4/IPv6 端口共用一个新连接配额；旧连接在关闭前保留，UDP 连接按 conntrack 超时释放。Agent 缺少 nftables、conntrack 或 NET_ADMIN 权限时会明确报告同步失败，不会静默跳过限制。Linux 隔离网络命名空间测试已覆盖混合协议、阈值更新、TCP 关闭和 UDP 超时释放。

本轮云主机矩阵测试期间，面板隔离规则同步曾出现长时间排队，部分连接客户端得到的是端口尚未监听而非超额拒绝，因此该部分结果未作为端到端通过证据；相关原始日志仍保留，不能据此宣称跨公网环境已完成验证。
