# 流量记账批处理与多用户操作验证（2026-10-26）

## 本轮改动

沿用现有 Node.js 架构，不增加 Redis，不改连接池上限，不发布或推送。对比基线见 [Agent 混合负载诊断](./agent-workload-2026-10-26.md)。

- 同一批上报涉及的用户锁按 ID 排序、每 64 个合并读取，不再逐用户往返数据库。
- 用户配额用分批 CASE UPDATE 累加，仅返回 ID、流量上限、用量、到期时间；MySQL 批量补读必要字段，SQLite／PostgreSQL 使用 RETURNING。余额、权限、到期和超额判断不使用展示缓存。
- MySQL 已有用户计数、规则计数、流量桶、运维日报及来源统计优先按主键 UPDATE，新记录才走插入及重复键兜底。保留流量累加、名称更新和唯一键语义。
- 仅流量记账事务选择开启冲突重试。确认回滚成功后，MySQL 死锁、PostgreSQL 死锁／序列化冲突最多执行三次；连接中断、锁等待超时、未知提交结果和提交后回调失败不自动重放。Agent 刷新事件在提交后发送。
- 补充批量流量、窄字段、回滚、并发累加、已有行无插入、字符串组合键与重试边界测试。

没有把全库规则读入内存再按用户分发。不同用户、权限、筛选、分页仍独立；相同展示请求沿用已有短缓存和在途请求合并。此次合并的是同一记账事务中的相关操作，不跨请求混合余额或配额决定。

## 测试口径

使用同一授权 2 核／约 2 GiB VPS，应用和发压共用 1.25 核／768 MiB 容器。外部数据库各限制 0.5 核，MySQL 128 MiB InnoDB、PostgreSQL 64 MiB shared_buffers，与基线一致；并非面板独占整机，也不是数据库性能排名。

场景为 10×300、100×30、300×20 主机／每主机规则，含每主机 5 个 TCP／ICMP／URL 服务、最多约 86.4 万条历史。每场景预热后投放 30 秒稳态、30 秒上报＋20 用户高频页面查询，再投放 30 秒多人读写。

走真实 HTTP／tRPC、JWT、Agent 加密认证、权限、路由与数据库，不启动真实 Realm、通知渠道或外部探测。CPU、SQL 采样有额外开销，短测不能给出生产 Agent 数硬上限。固定时刻投放，来不及发出的任务记 missed；阶段耗时包括等待在途请求结束。

### MySQL 最终轮

300 台／6,000 规则／20 人查询：稳态 P95 300→51 ms、失败 48→0；混合总 P95 26,156→14,749 ms，用户页面 P95 3,787→2,885 ms，SQL 32,454→16,549，失败／missed 从 42／60 降至 9／51。连接池等待峰值仍为 346。

最终轮三个阶段均为 **0 次 SQL 执行错误**，锁快照未再出现死锁记录，但这只说明本轮没有观测到，不保证所有拓扑和竞争下永不死锁。混合阶段仍有 9 次页面繁忙响应，流量上报仍显著排队；不能描述为“问题全部解决”或“300 台流畅”。该配置的数据库仅 0.5 核，累计 SQL 耗时也包含驱动排队。

额外叠加 50 人连续操作：50 个流程完成 48 个，443 次 HTTP 失败、809 个 missed；其余两次创建请求在客户端超时，不能据此认定服务端没有提交。已收到创建结果的 48 条记录核验无越权、端口冲突和删除状态错误；未收到响应的创建不在这一正确性结论内。流程 P95 54.63 秒，面板 CPU 单核约 90%，并不满足顺畅使用目标。

### PostgreSQL 最终轮

相同 300 台／6,000 规则／20 人查询：稳态 P95 73→40 ms；混合总 P95 12,243→771 ms，用户页面 P95 3,058→2,645 ms，SQL 28,338→16,645，失败／missed 从 13／50 降至 9／20。峰值池等待仍有 419，页面尾延迟并没有降到整体接口的 771 ms。

最终轮三个阶段同样 0 次 SQL 执行错误。50 人连续写阶段启动 50 个流程、完成 48 个，流程 P95 47.89 秒；343 次 HTTP 失败、437 个 missed。两次创建超时的服务端结果不明；已收到响应的 48 条创建记录通过归属、端口和删除状态核验，48 次预期越权写入实际被拒绝。面板 CPU 单核约 95%，仍不宜宣称 50 人连续改规则流畅。

## 多人同时操作

每个操作者按顺序：创建暂停规则、读取、尝试他人读写并核实拒绝、编辑、启用、重启、暂停、核对字段、删除、查询确认删除后不显示。每人最多每 15 秒启动一次流程，同一用户不重叠流程；同时仍每 2 秒查询规则、汇总、仪表盘，Agent 持续上报。

普通用户使用真实授权的端口转发组，不绕过资源权限。操作集中在少量入口主机上，属于较强竞争模型；新规则产生真实运行配置规划，但模拟器不执行真实 Agent 安装／转发动作。

| SQLite 场景 | 操作者 | 完成流程／启动流程 | 流程 P95 | 全阶段失败／missed |
| --- | ---: | ---: | ---: | ---: |
| 10×300 | 20 | 40／40 | 2.05 s | 0／0 |
| 100×30 | 50 | 50／50 | 35.77 s | 382／313 |
| 300×20 | 50 | 49／50 | 39.44 s | 347／427 |

100 台一轮所有写操作最终完成，失败来自后台页面繁忙响应；300 台一轮写操作也完成，但删除后的最后一次列表校验遇到繁忙，故整个流程只记 49 次完成，不算成功掩盖错误。两轮面板 CPU 达单核约 109%，不代表 50 人连续操作流畅。

所有已创建记录的最终核验均未发现越权、监听端口冲突或删除状态错误，预期越权更新全部被实际权限拒绝。基于 SQLite 的上述数字只代表该轮有限样本，并非超卖或全业务正确性的完整证明。

## 已识别的测试和实现问题

MySQL 第一轮只调整用户计数表后，锁快照又在规则计数表复现同类 PRIMARY supremum／insert-intention 环；扩大修正后，又在运维日报表发现同类问题。因此最终统一处理记账路径的这些已有行，不以某一表不再报错就宣称全部解决。中间轮诊断数据保留，不作为最终修复后的容量依据。

PostgreSQL 首轮多人操作使用显式 ID 预置数据，未推进数据库序列，导致后续真实创建与旧 ID 冲突。这是压测夹具问题，不是生产新增规则故障。已补充序列推进，首轮 PostgreSQL 的 operations 数字作废；此前没有新增记录的 steady／live 阶段仍可用于查询对比。

## 剩余限制

记账减少 SQL 往返后，连续增删改仍会触发权限、资源约束、运行计划、缓存失效等计算和查询。大批用户在少量主机上高频改规则时，Node 主线程、运行计划重算和事务排队仍会饱和；有界 503 保护继续保留，不能改成无限排队，也不能缓存余额／授权掩盖负载。

最终 CPU profile 的 operations 非 idle 样本中，GC 约 16%–18%；SQLite 的读取与语句准备、三种数据库的 ORM 构建也明显。外部数据库的驱动写入样本占比高，但不能仅据此判断是网络带宽瓶颈：包含协议处理、系统调用和受限容器调度，需结合数据库与操作系统进一步分析。

本轮不覆盖浏览器渲染、真实 SSE、转发吞吐、支付与库存竞争、长期运行、跨多个面板实例竞争及线上不同磁盘表现。客户端实际有轮询退避，模型未退避；相反，模型不运行真实 Agent 进程，二者均会影响生产负载。
