# 本地假数据压测（2026-10-20）

结论：优化前的主要瓶颈是流量统计扫描范围与重复计算，不是 SQLite 已达到性能极限。本次按用户收窄查询并改为后台刷新汇总后，相同假数据集的 100 持续并发吞吐从 128.8 提升到 439.5 请求/秒，P95 从 968ms 降至 255ms。不能据此承诺某配置 VPS 或 PostgreSQL 可以承载多少在线用户。

下文先保留原始基线，文末记录已实施优化、复测与限制。

## 环境与范围

- Windows 11，i5-12400（12 逻辑线程），15.8 GiB 内存，Node 22.19.0。
- SQLite WAL，数据库位于系统临时目录；后端通过 esbuild 按生产方式打包，发压端和后端为两个进程，但共享本机硬件。
- 500 个普通账户及 1 个管理员、50 台主机、10,000 条规则、240,000 条流量明细、240,000 条汇总桶、20,000 条余额流水。
- 使用真实 tRPC 路由、JWT、会话表和资源权限校验，不使用开发模式的自动管理员身份。预置会话，不压测登录、密码哈希和验证码。
- 验证了分页条数、不同用户的数据隔离、越权修改被拒绝、合法修改真实落库。
- 规则均为禁用的普通 iptables 规则，地址使用文档保留网段；不模拟真实隧道拓扑、执行转发、支付或关机。
- 不启动外部任务调度器、通知机器人和真实 Agent；优化复测仅额外开启本地汇总刷新。心跳阶段调用真实心跳处理器，但不包含 Agent 加密传输、流量批量上报或真实命令执行。
- 不读取 `.env`，子进程环境使用白名单，数据库、日志、密钥、迁移状态与开发环境隔离。基线采集时未修改业务实现；后续优化仅在本地，未发布。

每档测量窗口为 20 秒，结束后等待在途请求完成。分别记录接口 P50/P95/P99、错误、SQL 次数/耗时/执行计划、CPU、RSS、堆和事件循环延迟。SQL 计时包含 prepare 和执行，不包含连接锁排队；请求延迟包含排队。CPU profile 独立一档，不用于无采样吞吐对比。

## 负载与结果

普通用户场景轮流访问首页、规则、账单、主机，每次页面返回后等待 2 秒；首页发起 8 个接口，规则 2 个，其余各 1 个。起始用户在 1 秒内错峰进入。没有模拟浏览器查询缓存，因此比停留页面、偶尔点击更激进，也不是完整浏览器端体验测试。

持续并发场景没有思考时间，在 500 个不同账户间轮转，均匀请求上述 12 类接口；“100 并发请求”不等于“100 个在线用户”。

| 场景 | 请求数 | 请求/秒 | P50 | P95 | P99 | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 用户反复切页 | 345 | 17.2 | 11ms | 105ms | 113ms | 0 |
| 50 用户反复切页 | 1,596 | 79.8 | 27ms | 2,485ms | 3,148ms | 0 |
| 10 持续并发请求 | 2,535 | 126.3 | 80ms | 160ms | 184ms | 0 |
| 50 持续并发请求 | 2,544 | 124.9 | 399ms | 513ms | 561ms | 0 |
| 100 持续并发请求 | 2,669 | 128.8 | 778ms | 968ms | 1,072ms | 0 |
| 10 用户每秒修改一次规则名称 | 200 | 10.0 | 8ms | 21ms | 41ms | 0 |
| 压力解除后 10 用户切页 | 340 | 17.0 | 9ms | 116ms | 128ms | 0 |

50 用户切页的前 5 秒 P95 为 3,070ms，后 5 秒为 789ms，冷缓存和请求波峰影响明显；不是所有请求都耗时两三秒。持续并发从 10 增至 100 后，吞吐基本不再增长，只增加排队。

主轮完整测试共 22,468 次业务请求，另有 100 次模拟心跳。100/200 用户集中进入时存在本机 TCP `ECONNREFUSED`，并非业务接口返回 HTTP 500；这些档位不作为线上承载人数的依据。将测试监听 backlog 从 511 提高到 4,096 仍未消除，不能把错误简单归因为某个 backlog 数值。

补充将客户端连接池限制到 128：100 用户为 110.1 请求/秒、P95 7.75 秒，200 用户为 112.7 请求/秒、P95 14.98 秒，分别有 15/20 次 `ECONNRESET`。这些延迟包含客户端等待连接的时间，不能当作纯服务端处理耗时；也没有隐藏错误或自动重试。提高并发主要增加等待、没有带来吞吐提升，与持续并发档的瓶颈方向一致。本地 TCP/keep-alive 限制需要在独立 Linux 发压机复核。

后台心跳档使用 50 台假主机、每台约 10 秒一次，共 100 次心跳；在 100 用户切页下，心跳 P95 约 6.94 秒、心跳错误为 0，业务请求 P95 约 6.05 秒（含上述建连错误）。这是后台规划/数据库操作争用的风险信号，不是完整生产 Agent 容量结论。

## 已确认的热点

### 1. 用户流量查询没有先缩小到用户规则集合

位置：`server/repositories/metricsRepository.ts` 的 `getGlobalTrafficSeries()`、`getTrafficSummaryRowsFromBuckets()` 和 `getTrafficSummaryRowsFromStats()`。

当前使用 `COALESCE(parent.userId, fr.userId, ...) = ?` 处理转发组父子规则归属。逻辑保证了归属正确性，但本轮 SQLite 执行计划表现为：

- 趋势查询 `SCAN fr`，遍历规则后查明细，再做用户归属筛选和临时分组。
- 汇总桶查询仅用到索引的 `bucketMinutes` 前缀，扫描大量其他用户的桶，再关联规则、父规则并筛选。
- 用户仅有 20 条规则，但查询成本受到全站 10,000 条规则和 240,000 条历史记录影响。

100 持续并发档，分类桶查询累计约 6.71 秒、分类明细查询约 3.52 秒、趋势查询约 3.41 秒，合计占 SQL 耗时 **87.4%**。独立 profile 中原生 SQLite `all()` 占采样时间约 **70.5%**。

### 2. 分类统计会同时读取汇总桶和原始明细

`getTrafficSummaryByRule()` 即使成功取得桶，也会读取原始明细。这是为防止历史版本桶更新不完整而低估流量，不能直接删掉兜底。当前两个查询都存在广范围扫描，形成叠加成本。

首页趋势使用 60 分钟粒度，而直接使用汇总桶的分支要求 30 分钟；本轮实际命中明细聚合路径。后续可评估从较小粒度桶安全聚合，而非简单改显示粒度。

### 3. 同步 SQLite 会把慢统计扩大到其他接口

`server/dbRuntime.ts` 中 better-sqlite3 的同步执行与单连接锁使其他请求等待。100 持续并发时事件循环 P99 约 **967ms**；发压进程事件循环 P99 约 25ms，CPU 约单核 1.3%，发压端 JS 计算不是这档的主要瓶颈。

本轮 RSS 峰值约 **476 MiB**，压力解除后 RSS 仍保留较高水位；堆有 GC 回落。没有做长时间稳态和堆保留分析，不能据此证明有或没有内存泄漏。

## 只读 SQL 对照实验

在同一假数据库上，预取用户的 20 条规则 ID，再约束统计查询的 ruleId 范围。交替执行原查询和对照查询各 20 轮，核对这份数据的返回结果相同：

| 查询 | 原查询平均 | 缩小范围后平均 | 局部差异 |
| --- | ---: | ---: | ---: |
| 首页趋势 SQL | 18.91ms | 0.26ms | 约 72 倍 |
| 分类汇总桶 SQL | 37.02ms | 0.37ms | 约 101 倍 |

这只是 SQL 局部实验，不是全站提速倍数，也不包含预取规则 ID 的时间。假数据没有转发组子规则和孤立历史；正式优化必须保留父子规则归属、已删除规则历史、转移用户后的归属和权限隔离，不能照搬实验替换生产逻辑。

## 后续建议与未覆盖项

1. 优先优化统计查询的过滤顺序与索引使用，再复测同一数据集；补齐父子规则、已删除历史和多数据库回归。
2. 设计可靠的桶完整性标记/增量补偿，避免长期每次都全量双读；不能牺牲计费准确性。
3. 次级候选：首页缓存上限为 250 个键、一个用户会占多个键；权限 scope 缓存仅 1 秒且会加载拓扑。多用户会放大重算，尚未做独立缓存 A/B。鉴权每个请求还会两次查询活跃会话，可考虑请求内复用，不应取消撤销会话检查。
4. 在隔离 Linux + PostgreSQL/MySQL 环境，按真实主机数、历史保留时长、Agent 心跳/流量/探测频率补测。不能把本机结果折算成某配置 VPS 的在线人数。

本轮未覆盖：注册/登录风暴、支付回调、通知发送、Excel 导出、管理员全站大查询、真实转发组/隧道重规划、长时间运行、数据库故障和多实例。规则写入只验证了名称更新，未代表规则创建、端口分配和删除峰值。

## 已实施优化

- 流量查询先从 `userId` 索引获得所属规则及合法模板的子规则，再通过 `ruleId` 索引读取流量明细、桶和累计计数；不再先扫描所有用户的流量再过滤。保留历史归属、已删除记录及不完整桶的明细兜底，未简化计费口径。
- 修正多数父规则 ID 为空时 SQLite 选择全表扫描的计划：增加等价的 `IS NOT NULL` 条件，沿用现有父规则索引，无需新建索引或迁移历史数据。
- 授权拓扑只从本人的资源、有效授权、订阅和可用按量资源出发，分批加载可达组/隧道；保留循环防护和使用权限边界，不把组内节点提升为独立使用授权。
- 普通用户的非分页主机列表也在数据库中筛选归属/授权，不再读取全站主机后过滤。管理员的主机管理仍是全局管理页面；首页统计、我的规则、看板默认自身范围保持不变，只有主动选择其他用户/全部时才扩大数据范围。
- 同一请求内复用已验证的会话与当前用户资料，减少重复读取；没有跨请求缓存鉴权，不延迟禁用账户或撤销会话的校验。
- 首页展示汇总、运维流量和财务汇总按账户及筛选范围独立保存结果，后台约每分钟刷新。冷启动/新范围仅计算该范围，重复请求不触发汇总重算；只维护近期访问的范围，不定时遍历所有注册用户。
- 后台串行刷新、任务防重入、请求间让出事件循环；首页每轮预算 100ms，看板 25ms（单次计算可能超出软预算）。冷加载合并并发；失败保留旧结果并退避重试。空闲 15 分钟淘汰，首页最多 5,000 键/32MiB 序列化数据，看板独立 300 键/8MiB，不代表进程 RSS 上限。
- 规则配置修改和统计重置后使相关用户首页汇总失效；数据库关闭/切换时清空汇总，防止不同数据库中相同用户 ID 复用旧结果。事务中的失效在提交后执行。

以上是查询与缓存的逻辑隔离，不是每用户一个数据库。共享的授权资源仍可读取其必要配置；余额、额度校验、流量写入和扣费保持实时，不经过展示汇总缓存。汇总存于进程内，重启后按访问生成；持久化明细、桶与计数器不受影响。

## 优化后复测

相同硬件、500 用户、10,000 规则、各 240,000 条明细/桶、20,000 条流水；每档 20 秒，SQL 采样开启。基线为 `http-full.json`，中间轮为 `optimized.json`，最终轮为 `optimized-final.json`，最终 CPU 分析为 `optimized-final-analysis.json`。包含真实鉴权、管理员默认自身/显式全部、用户隔离和越权拒绝的语义检查。

| 场景 | 优化前请求/秒 | 优化后请求/秒 | 优化前 P95 | 优化后 P95 | 最终轮错误 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10 用户切页 | 17.2 | 17.0 | 105ms | 19ms | 0 |
| 50 用户切页 | 79.8 | 85.0 | 2,485ms | 27ms | 0 |
| 10 持续并发 | 126.3 | 427.2 | 160ms | 31ms | 0 |
| 50 持续并发 | 124.9 | 438.0 | 513ms | 134ms | 0 |
| 100 持续并发 | 128.8 | 439.5 | 968ms | 255ms | 0 |
| 10 用户每秒改名称 | 10.0 | 10.0 | 21ms | 27ms | 0 |
| 压力解除后 10 用户切页 | 17.0 | 17.0 | 116ms | 23ms | 0 |

切页档有固定思考时间，请求/秒不是容量上限；名称修改未加速，P95 小幅波动，不能宣称所有接口均提升。中间优化轮 100 持续并发为 396.9 请求/秒、P95 295ms；补充父规则空值计划修正后最终为 439.5/255ms，非只挑单次最快结果。

100 持续并发的 SQL 总时间从约 15.59 秒/档降至 5.44 秒/档，事件循环 P99 从约 967ms 降至 277ms。优化后执行计划中，流量数据按 `ruleId`、孤立历史按保存的 `userId` 寻址；当前热点已转向用户资料读取、SQL 构造和较小范围的聚合，不能把结果称作 SQLite 引擎的极限性能。

独立 CPU profile 中 `.all()` 从基线约 70.5% 样本占比降到约 13.1%；采样、测试包装及 GC 也有开销，profile 档吞吐不与无采样档混用。

### 限制和待验证

- 最终轮 100 用户切页无错误，P95 493ms；但其基线存在建连失败，因此不把两轮直接当作稳定容量对比。
- 200 用户同时进入仍有 765 次本机 TCP `ECONNREFUSED`；100 用户与模拟心跳同跑时有 51 次客户端连接错误。该心跳档的 100 次模拟心跳均成功，P95 约 901ms。没有自动重试掩盖错误，不能宣布 200 用户进入波峰已稳定，也尚不能断言连接问题只来自 Windows。
- 早期快速/中间复测也出现过 `ECONNRESET`，并非所有轮次均零错误；表格列的是最终轮对应档位，不删除异常记录。
- 最终长轮 RSS 峰值约 1.09GiB，高于基线约 476MiB；堆从约 874MiB 回落到 346MiB，汇总序列化数据仅约 2.3MB。吞吐提升不等于内存下降。补充关闭 SQL 采样的 80 秒测试，100 并发为 458.0 请求/秒、P95 243ms，各档无错误，RSS 峰值约 216MiB；全部计时结束后两次手动 GC，存活堆约 46.7MiB、RSS 202.8MiB。说明此前大峰值不能直接等同持续占用，不能把峰值全归因于新缓存，也不能据此排除长期泄漏或承诺小内存 VPS 的同等吞吐。该补测未包含心跳，与完整轮存在负载差异，原始指标见 `optimized-memory.json`。
- 本次未做实际 MySQL/PostgreSQL 压测。SQL 使用既有方言工具，但跨数据库负载、真实拓扑和 Agent 批量记账仍需隔离环境补测。没有擅自启用生产外部任务、推送版本或改动真实开发数据。

新增回归覆盖：逻辑父子归属/无效父引用、孤立历史、管理员自身/全部范围、5,000 条无关规则的执行计划、301 个授权组的分批与循环、只含主机的用户不读取拓扑成员表；后台合并冷请求、过期读取不重算、失败重试、失效后旧任务不能复活、LRU/大小/空闲淘汰。

```powershell
node scripts/load-test.mjs --no-sql --gc-check --stages=saturated-10,saturated-50,saturated-100,read-recovery-10 --output=dist/load-test/optimized-memory.json
```
