# 短缓存与并发读取压测（2026-10-23）

本轮在现有按用户查询、后台汇总的基础上，增加展示短缓存、同键请求合并和有界加载队列。使用本机真实 HTTP/tRPC、JWT、会话表及 SQLite 假数据进行修改前后对比，不代表线上服务器的承载人数。

## 环境与负载

- Windows 11，Intel i5-12400（12 逻辑线程）、16 GiB 内存、Node.js 22.19.0；服务与发压进程在同一台电脑。
- 两组独立数据：50 用户/1,000 规则/各 24,000 条流量明细和汇总桶；500 用户/10,000 规则/各 240,000 条明细和汇总桶。各有 50 台假主机，每用户 40 条余额流水。
- 使用系统临时目录的独立 SQLite，未读取 `.env`、未修改 `.dev/forwardx-dev.db`；外网请求禁用。后台仅启动本地汇总刷新，不启动真实 Agent、探测、支付或通知。
- 混合读取共 12 类接口：首页 5 类、余额、按量状态、订阅、规则列表/汇总、余额流水分页、主机分页。包含实时认证开销，不模拟浏览器端缓存，不压测登录和密码哈希。
- 每档持续 20 秒、50 或 100 个并发请求，无思考时间；在对应数量的用户之间轮转。50 用户场景用于观察短期重复访问，500 用户场景用于观察低命中率影响。没有跨用户共享私有规则/流量结果。
- 结果包含 SQL 计数开销、HTTP 建连和排队，不自动重试请求。接口加载无人工延迟。

## 实测结果

对比与原始结果位于本地 `dist/load-test/`；该目录是可重新生成的产物。

| 用户数 | 持续并发 | 优化前请求/秒 | 优化后请求/秒 | P95 前 → 后 | SQL/请求 前 → 后 | 错误 前/后 |
| --- | --- | --- | --- | --- | --- | --- |
| 50 | 50 | 427.7 | 480.0 | 140.1 → 139.4ms | 6.19 → 4.78 | 0/0 |
| 50 | 100 | 390.8 | 521.7 | 342.2 → 220.7ms | 6.11 → 4.76 | 0/0 |
| 500 | 50 | 322.6 | 376.6 | 238.8 → 155.2ms | 7.38 → 7.28 | 0/0 |
| 500 | 100 | 362.2 | 422.4 | 355.9 → 276.4ms | 7.27 → 7.05 | 0/0 |

上表来自本轮完整阶段对比（`cache-hot-before.json` / `cache-hot-final.json`、`cache-before.json` / `cache-wide-verified.json`）。热点场景每请求 SQL 约减少 22%；低命中率场景收益更小，不能通过共享其他用户的数据来人为提高命中率。吞吐提高时总 SQL 次数可能增加，因此按 SQL/请求比较数据库开销。单机单轮结果存在波动，不承诺固定提升比例。

另测 10 个写入 worker、每次写后等待 1 秒：200 次更新、0 失败、P95 29.2ms；随后 10 用户切页读取 340 次、0 失败、P95 17.8ms。写入真实落库，并验证修改前缓存过的列表立即返回新名称。

完整热点阶段服务进程峰值 RSS 约 224 MiB；阶段结束后的独立 GC 诊断 heap 44.4 MiB、RSS 216.5 MiB。GC 不在计时区间执行。RSS 包含 V8、SQLite、原生分配器及其他模块，不能视为展示缓存大小，也不能据此判断长期无内存泄漏。

500 用户最终复测的服务峰值 RSS 约 212 MiB，100 并发档结束时展示缓存约 1.95 MiB（499 键）；独立 GC 后 heap 48.8 MiB、RSS 204.0 MiB。此前复测 `cache-after.json` 的同档为 432.1 请求/秒、P95 268.2ms；最后的 `cache-wide-verified.json` 已包含过期键按秒清理。

补充在最终代码上直接从冷进程运行单个 100 并发档（不先运行 50 并发档）：50 用户为 455.8 请求/秒、P95 293ms、SQL/请求 4.81；500 用户为 324.3 请求/秒、P95 422ms、SQL/请求 7.25，均无失败。对应 `cache-hot-current.json`、`cache-current.json`。这些数字包含更多首次计算，不能与上表已经先运行 50 并发档的结果直接算提升比例，也说明冷启动、大量不同用户首访时短缓存不能消除所有慢查询。

## 缓存与过载策略

- 规则/主机分页：2 秒缓存，无过期列表回退；资源访问标记/主机可见范围仍按请求处理。
- 规则汇总、主机状态/指标、链路流量：2 秒新鲜期，随后最多 8 秒可先返回旧值并合并刷新；不改变原有流量统计口径。链路当日统计的键包含北京时间日期，跨日不复用昨天的结果。
- 用户、角色、所有/自己的范围、筛选及可见资源集合区分缓存；普通用户修改清理自己的及管理员相关展示，管理员修改清理全部展示。数据库切换清空，旧加载不得回填。
- 物理主机指标允许已授权查看者复用同一组主机的结果；每次请求仍检查访问权限。撤权后不能通过命中的共享指标缓存继续读取。
- 新展示缓存有 2,000 键/24 MiB 序列化数据上限，按 LRU 淘汰并定期回收过期项；序列化预算不等于真实 JS 堆内存。
- 展示加载与首页、运维汇总共享 16 个加载槽，最多等待 128 项，排队超过 2 秒或队列满则明确返回 HTTP/tRPC 503，不无限排队。已执行 SQL 的槽位只在真正结束时释放，不用超时伪装取消 SQL。
- 鉴权、会话撤销、余额校验、支付/兑换/扣费及流量限制执行不使用该展示缓存。首页原有后台刷新频率保持不变。

## 验证覆盖

自动化测试覆盖冷缓存 100 请求合并、TTL 过期刷新合并、繁忙时旧指标先返回、队列长度/等待上限、排队后恢复、同步异常、刷新失败退避、键/字节预算、失效与旧请求竞态、用户/角色/筛选隔离、管理员默认自己的与显式全部、修改后立即刷新、撤权后禁止读共享指标、数据库切换清空。

相关资源流量、个人分组、会话禁用及安全并发测试通过；TypeScript 检查和服务端构建通过。队列极限和慢查询保槽行为使用可控 Promise 单元测试验证，未声称 HTTP 压测已把所有过载分支触发。

## 复测

```powershell
pnpm test:performance
node scripts/load-test.mjs --users=50 --stages=saturated-50,saturated-100,writes-10,read-recovery-10 --gc-check --output=dist/load-test/cache-hot.json
node scripts/load-test.mjs --stages=saturated-50,saturated-100 --gc-check --output=dist/load-test/cache-wide.json
```

SQLite、MySQL、PostgreSQL 均复用同一服务端缓存/队列逻辑。本轮仅实测 SQLite，没有本地 MySQL/PostgreSQL 服务器，不能将数字直接套到其他数据库或 VPS。并发请求数也不等于在线用户数。未覆盖完整浏览器渲染、真实 Agent 上报争用、长时间浸泡和多实例部署；多实例缓存各自独立，权限检查仍执行，但展示失效不跨进程广播，其他实例依赖短 TTL 收敛。
