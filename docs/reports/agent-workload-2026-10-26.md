# Agent／规则／服务混合负载诊断（2026-10-26）

本篇保留优化前基线。后续批处理修正和多人增删改复测见[流量记账优化验证](./traffic-accounting-optimization-2026-10-26.md)，不要将本篇的已发现问题描述当作后续代码状态。

## 结论与范围

保留现有 Node.js 架构。本轮新增隔离压测工具与报告，没有拆分 Go、修改生产业务实现、调大连接池、发布或推送；已有其他改动保持不动。

压力不只由规则总数决定：主机上报次数、每批涉及的用户数量、页面查询频率都会影响。SQLite 的热点包括同步 SQL、ORM 构建、对象分配／GC、页面聚合；MySQL 另复现真实记账死锁。换语言或 Redis 不能直接消除这些事务问题。

授权 VPS：Debian 13，2 vCPU Xeon E5-2682 v4，约 1,974 MiB RAM，Node 22.23.4。

- 面板与发压父进程共用容器 1.25 核／768 MiB，CPU 分开记录；不是面板独占整台 2 核。

## 负载与有效性

正式结果均为 `fixtureProtocol: 2`：走真实 Express／tRPC、JWT、权限校验、Agent AES-CTR＋HMAC 与 v1 签名认证，不用明文 token 绕过。

- Presence 每 5 秒；完整心跳固定每 60 秒。
- 流量每 30 秒；被查看的前 24 台主机每 10 秒。
- 服务结果每 30 秒；未变化规则探测模拟 5 分钟闸门。
- 被查看主机每 3 秒发 `busy=true` 指标心跳，避免把指标刷新误模拟成完整规则规划。
- 管理员每 2 秒查看主机分页、24 台指标／流量并续租 watch，每 10 秒查一个主机服务图表。
- 20 名普通用户每 2 秒各发一个真实 tRPC batch，含规则分页、规则汇总、仪表盘三个查询。

每轮 **30 秒稳态＋30 秒上报和页面混合负载**。固定时刻投放、有界在途请求，任务来不及执行记 `missed`，不以慢请求后减少发压来隐藏超载。P95 含错误响应；batch 内业务错误也计失败。

这是接口压力模型，不是完整 Agent 调度器或浏览器集群。真实 SSE、服务周期、快慢心跳策略会改变频率。未建 SSE，不覆盖 v2 挑战认证、支付、通知发送、清理、长期运行及大量同时改规则。**短测不能给出 Agent 数硬上限，也不是数据库性能排名。**

发压前预热本地状态与分段签名，验证健康监听不产生重新安装动作、稳态命中快速心跳。检查用户数据隔离、三类服务落库、指标落库、流量增长、冻结批次重试不重复计数；结束后检查原会话有效。

探索轮发现模拟器本地状态签名格式错误，导致反复规划。已改为合法十六进制签名，加回归测试并重跑。**探索轮延迟／吞吐数字全部排除**，下表只用修正后的正式轮。

## SQLite 正式结果

CPU 为面板占一个核心的比例，不是整机百分比。总 P95 受大量便宜的 Presence 请求影响，另列用户页面 batch P95。

| 场景 | 稳态总 P95 | 稳态 CPU | 混合总 P95 | 页面 P95 | 混合 CPU | 失败／missed |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 10 × 300 | 121 ms | 12% | 145 ms | 144 ms | 57% | 0／0 |
| 100 × 30 | 62 ms | 33% | 352 ms | 970 ms | 77% | 0／0 |
| 300 × 20 | 52 ms | 58% | 588 ms | 2,482 ms | 86% | 4／23 |

三组稳态均零失败、零 missed，全程无 SQL 执行错误。300 台混合阶段 4 次失败来自页面 batch 的“服务繁忙”503 子响应（外层 HTTP 207），不是认证失效。

300 台混合阶段事件循环利用率约 93%，事件循环 P99 延迟 154 ms，面板峰值 RSS 224 MiB，30 秒执行 28,687 次 SQL。流量及服务上报无失败但变慢，结束后登录有效。短时过载可先影响页面，不必等内存耗尽。

同为 3,000 条规则，100 台比 10 台上报次数更多，每批用户分布也不同，不能只归因规则数。300 台稳态总 P95 更低也不代表容量更强，只是接口组成不同。

## 外部数据库正式结果

均为 300 台、6,000 条规则、1,500 个服务／主机组合、20 用户混合查询。

| 数据库 | 稳态总 P95 | 稳态失败 | 混合总 P95 | 页面 P95 | 混合失败／missed | 池等待峰值 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| MySQL | 300 ms | 48 | 26,156 ms | 3,787 ms | 42／60 | 266 |
| PostgreSQL | 73 ms | 0 | 12,243 ms | 3,058 ms | 13／50 | 348 |

MySQL 稳态 48 次及混合 28 次流量上报失败均对应死锁；混合另有 14 次页面 batch 失败。PostgreSQL 无 SQL 错误，13 次失败均为页面忙时保护。两种数据库均未 OOM，结束后原会话仍有效。

最慢的是流量路径：MySQL 混合流量上报 P95 29.10 秒，PostgreSQL 16.21 秒。即使数据库 CPU 有余量，长事务、驱动排队和逐用户操作也会放大等待；不能只看 Node CPU 未到 100% 就判断没有瓶颈。

每阶段只投放 30 秒，随后等待已发请求完成，因此 MySQL 混合阶段实际 53.35 秒，PostgreSQL 37.81 秒。CPU 平均和 RPS 均包含排空时间。池等待为每 100 ms 采样观察值，不是连接数，也不能排除更短暂峰值。外部 SQL 耗时含驱动排队及网络，多查询并行累加不能视为墙钟时间。

外部数据库只有 0.5 核、较小缓存，且与发压共用低配机器；此表不表示 PostgreSQL／MySQL 通常比 SQLite 慢。当前模型也没有浏览器轮询退避，流量失败批次不重试，因此不能直接换算线上错误率或数据损失量。

### MySQL 死锁已在正式轮复现

流量接口出现 `ER_LOCK_DEADLOCK`／1213，返回 500。正式轮 InnoDB 快照：

- 两事务分别 UPSERT 用户 2–21、62–81 的 `user_traffic_counters`，用户不重叠。
- 均持有 PRIMARY 末端 `supremum` 的 X 锁，并等待插入意向锁，形成环；数据库回滚一个事务。
- 该复现已使用修正签名，不依赖错误的重复规则规划。

按用户串行及锁用户行，仍无法排除自增主键／UPSERT 间隙竞争。当前事务封装回滚并抛出，没有整事务有限重试。锁快照已保留。不建议只扩大池或全局更改隔离级别掩盖问题。

## 优先优化方向

1. **记账事务正确性。** `metricsRepository.ts:698` 用户计数 UPSERT 与去重、其他写入交互。后续应减少已有行插入路径、统一锁序，考虑有界整事务重试，保留批次幂等及提交后回调语义。
2. **逐用户小查询。** `agentReportRoutes.ts:785` 每批记账、`trafficBillingRepository.ts:36` 逐用户取锁、`userRepository.ts:848` 流量更新。后者返回完整用户，MySQL 还追加读取。300 台 SQLite 混合阶段单此更新执行 6,940 次。批量优化不能跳过余额／配额判定。
3. **汇总与构建开销。** 减少规则页重复流量聚合、收窄字段、复用请求内计算；展示缓存不能用于过期计费判定。
4. **主线程负担。** 300 台 SQLite 混合 CPU 非 idle 采样中，Statement 准备约 11%、读取约 10%、GC 约 10%；Drizzle 类型判断／查询构建也显著。是含观测开销的近似采样，不是精确生产 CPU 分摊，不能全归咎磁盘 SQL。
5. **保留有界保护。** 503 是忙时保护，不应取消后无限排队；增大池不能解除死锁，也不能增加 Node 单线程算力。

只读 EXPLAIN 显示用户流量查询使用规则所有者及 `(bucketMinutes, ruleId, bucketStart)` 索引；派生结果 `SCAN b` 不是全库历史扫描，未误判“所有索引失效”。

建议继续优化现有 Node＋数据库链路。当前证据不支持先拆 Go；同样的逐用户写入、锁竞争及汇总即使换语言仍存在。
