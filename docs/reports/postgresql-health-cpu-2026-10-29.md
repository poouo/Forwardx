# PostgreSQL 启动与 CPU 占用排查（2026-10-29）

## 结论

已确认并修复 PostgreSQL 启动重复改表、吞掉迁移错误，以及单次超时就将整个面板判为数据库不可用的问题。报告中的持续高 CPU 尚未在本地复现，不能将这些修改描述为已经根治 CPU 问题。

## 已确认的问题与处理

- PostgreSQL 原迁移逐列尝试 `ADD COLUMN`，依赖异常跳过已有字段；索引及字段的真实错误也被吞掉。现在批量读取目录，按照实际 `search_path` 查找已有表、字段及索引，仅补齐缺失项，并保留权限、存储、唯一性及锁错误。
- 默认设置改为一次批量写入，保留已有值。结构完整时，重复启动的 schema 阶段只需 7 条查询，不执行建表、改表或建索引。
- 健康检查默认独立连接超时从 3 秒调整为 6 秒；已初始化数据库的短暂故障需连续 3 次失败确认，成功即清零。启动失败和明确认证、证书、已识别的存储错误不等待确认。
- 单条业务 SQL 超时仍失败、保留认证凭据，也不自动重放不确定的写操作，但不再单凭它切换所有用户到数据库故障页。受保护数据库操作的超时在 tRPC 中仍返回脱敏的 503，不会因全局状态保留健康而暴露查询文本。
- 暂时失败日志包含失败次数、实际耗时及事件循环忙碌比例，最多每分钟一次；该比例不是 CPU 根因判定。

## 实测环境和结果

环境：Windows x64、Ryzen 7 9700X、Node 22.23.1、原生 PostgreSQL 18.4。所有数据库、账号、规则和流量均为隔离测试数据，数据库及 HTTP 测试仅监听本机；没有连接现有业务库。

使用实际 `dist/index.js` 启动完整后台任务，模拟 9 个 Agent、54 条规则，Agent 心跳每 10 秒、流量上报每 30 秒；页面查询阶段另有约每秒一次登录态查询。每个阶段约 65 秒，使用内置 Inspector 采样，不开放调试端口。

| 当前代码阶段 | 单核 CPU | 失败请求 | 事件循环忙碌比例 |
| --- | --- | --- | --- |
| 空闲，后台任务开启 | 2.28% | 0 | 0.32% |
| Agent 持续上报，后台任务开启 | 3.72% | 0 / 90 | 1.15% |
| Agent 上报 + 页面查询 + 后台任务 | 3.17% | 0 / 150 | 1.10% |

这三轮没有出现数据库健康超时；CPU Profile 中空闲采样约占 98.6%–99.5%，未发现持续运行的单一热点。采样工具本身也有开销，短期 RSS 增加不能单独解释为泄漏。

另从本地 `v2.3.292` 标签构建，在同机、克隆测试库上运行：schema 初始化耗时约 56.45 秒；初始化完成后的 Agent + 页面阶段，单核 CPU 约 3.60%，150 个请求零失败，同样没有复现报告里的持续 55%–85%。旧版第一个采样阶段包含启动过程，不作为空闲基线。当前完整面板启动约 276 毫秒；这是版本整体对比，不是将全部改善单独归功于本次 schema 修改。

额外修复了压测工具的问题：它改写受保护连接池的 `connect/getConnection` 方法，可能让连接获取重新进入自己的队列，产生工具自身的 503。现在仅在物理连接上记录 SQL。修正后原生 PostgreSQL 稳态压测 30 秒：73 个请求、零错误、p95 约 14 毫秒、单核 CPU 约 3.0%、连接池等待峰值为 0。该问题属于测试工具，不是生产面板 CPU 根因。

## 验证范围

- 原生 PostgreSQL 18.4：空库初始化、补齐字段/索引、保留用户及设置、二次启动无 DDL、`search_path` 回退，已实际执行通过。
- PostgreSQL 18.6（PGlite 嵌入式引擎）：DDL 和目录查询交叉验证通过；它不模拟 Docker 网络。
- 回归测试覆盖单次及连续失败、恢复、认证/证书/SQLite 存储故障、查询黑洞、会话不丢失、tRPC 超时脱敏和队列不递归。
- CI 已增加 PostgreSQL 12 / 18 服务测试配置；本次未推送，远端 CI 尚未执行。本地没有 Docker，不把 Windows 原生测试描述为 Docker 验证。

## 仍不能下结论的部分

模拟数据量、数据库次版本、CPU、操作系统、容器限制、历史长度及上报分布都与用户现场不同；本次没有真实转发隧道、长时间 SSE 连接或 44 小时持续负载。因此这些数据不能排除现场问题，也不能证明用户机器或数据库有问题。

报告把 ORM 识别为 Kysely，但项目使用 Drizzle；`node-postgres/session.js` 是数据库查询执行器，不是网站登录会话。Agent 路由也不逐请求走网站的 `createContext`。数据库 TPS 不等于 HTTP 请求数，不能用它推导每请求 CPU 耗时。75 秒没有慢 SQL、日志固定间隔恢复，都不足以证明整个观察期绝无数据库或网络问题。

如果后续仍有高占用，应区分面板进程 CPU、事件循环延迟、数据库查询/连接耗时与容器 CPU 限额或节流；再按异常发生时的实际采样定位热点。不能只提高超时、关闭鉴权或删掉流量计费来掩盖故障。

环境变量和故障确认延迟见 [环境变量](../guide/env-vars.md#数据库健康检查)。本次未升级版本号、未推送、未发布。
