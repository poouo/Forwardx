# 数据库驱动与离线 IP 库按需加载（2026-11-03）

## 本次改动

- SQLite、MySQL、PostgreSQL 驱动及其 Drizzle 适配器在需要时加载；初始化、测试连接、健康检查、迁移目标和旧库迁移命令均按数据库类型选择，不在导入路由时提前加载全部驱动。
- 数据库迁移仍可同时访问源库与目标库；临时连接沿用原有关闭流程。Node 会缓存已导入的驱动代码，因此迁移结束后不承诺卸载模块本身，也不代表会运行多个数据库服务。
- 离线 IP 数据按 IPv4/IPv6 独立首次加载，同一族并发查询共用加载过程。最后一个查询结束后空闲 60 秒，删除缓存引用，让大缓冲区可以被回收。活动查询不会被中途释放。
- 数据文件校验、离线查询和数据库中的地址结果缓存保留；损坏或缺失文件不永久缓存失败，文件恢复后可重试。不在生产中调用强制 GC。

## 对比条件

- Windows、Node.js 22.23.1；esbuild 使用与生产相同的 Node 22 ESM / external packages 设置，不在测量进程加载 tsx。
- 使用 `scripts/load-test/server.ts` 隔离测试入口，每组 3 个新进程，各自创建临时 SQLite。固定 30 台假主机、10 条禁用规则、1 个普通用户及管理员、240 条流量明细、240 个汇总桶、40 条流水。
- 使用真实业务路由、数据库结构和本地汇总 worker；没有实际 Agent、转发连接、通知、支付请求和生产后台任务，禁止外网 fetch。因此不是完整生产面板的容量测试，也不是 Linux/Docker 内存承诺。
- 优化前仅将本次修改的数据库运行时、健康检查、数据库切换、面板迁移和 IP 库模块恢复为 `bf972f3c7d29cbcf241690bb25dc9dc8a889e926` 中的源码后构建；其他现有本地更改在两组保持一致，没有重置工作区。
- 内存快照均经过事件循环让步和两次诊断 GC。IP 空闲时间通过 Node 测试虚拟定时器推进 60,001ms，验证缓存生命周期，不代表真实等待一分钟后的 OS 回收时延。
- 专项脚本和原始结果位于本地忽略目录 `.dev/memory-lazy-comparison.mjs`、`.dev/memory-lazy-comparison-results.json`。

## 结果（三次中位数，MiB）

| 阶段与指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| SQLite 样例初始化后 RSS | 186.86 | 186.91 |
| 同阶段 heapUsed | 42.38 | 39.79 |
| 双栈 IP 库加载后 RSS | 235.87 | 235.29 |
| IP 库空闲过期并 GC 后 RSS | 235.88 | 189.25 |
| 同阶段 arrayBuffers | 46.33 | 0.17 |

优化前 SQLite 进程包含 `mysql2`、`pg`、`better-sqlite3`；优化后仅包含 `better-sqlite3`。

驱动按需加载减少约 **2.59 MiB 已用 JS 堆**，但本次进程 RSS 基本不变，不能声称它单独显著降低了系统内存。共有的 SQL、表结构、业务模块仍然需要加载。

IP 库空闲释放减少约 **46.16 MiB ArrayBuffer**，空闲阶段 RSS 相比优化前约少 **46.63 MiB**。只查询 IPv4 时对应数据约 10.61 MiB，IPv6 约 35.55 MiB。持续查询时仍复用数据，避免反复解压；首次解压的瞬时峰值并未消除。生产环境何时回收、何时归还 OS，仍由 V8 和内存分配器决定。

## 首次评估的后续方向（部分已在追加优化中完成）

1. **低频后台依赖延迟加载**：首次评估时，`billingExport.ts` 顶层导入 ExcelJS，完整面板会经导出路由加载。在同一隔离入口中，额外导入 ExcelJS 约增加 6.9 MiB 已用 JS 堆。此依赖已在下述追加优化中改为按需加载；首次导出后模块仍会缓存。迁移、AI/机器人等模块也可按依赖图逐项评估，不应直接延迟全部鉴权或关键路由。
2. **真正可卸载的低频任务**：若要求导出、解压等执行后连依赖也一并回收，可考虑受限 worker/子进程。需要限制并发、设置超时并流式传递数据，避免复制大快照抵消节省；这是架构改动，应单独测试，不给未实测的节省承诺。
3. **缓存与连接池进一步分档**：现有展示、汇总缓存均为有上限、按实际使用增长，并非启动即占满。小规模样例没有证据表明降低上限会明显降低基线；贸然缩减反而增加数据库查询。下一步应采集真实命中率、条目字节数和池中实际连接数，再决定小内存档位。
4. **更低的 IP 库查询峰值**：可评估文件/向量索引查询替代全量解压，代价是文件 IO、部署管理和并发句柄复杂度。目前采用空闲释放方案，优先保证批量查询速度与兼容性。

## 常规运行追加优化

按用户要求只优化日常运行，不改备份/迁移格式和执行逻辑，不降低展示缓存容量或有效期，也不通过缩小 V8 堆来制造内存下降。

### 已完成

- **可选功能依赖按需加载**：ExcelJS 在真正生成账单文件时加载；Nodemailer 在邮件启用、配置完整且要发信时加载；Telegram 的独立 Undici 依赖及连接池在真正发起请求时加载/创建；Cap 引擎在首次生成 Cap 挑战时初始化。并发首次调用共用单个 Cap 实例和 Telegram 连接池，原来的鉴权、限频、token 单次消费、IPv4 优先、TLS 验证及请求取消策略保留。同步图片验证码接口不变。
- **展示/图表缓存空闲清理**：原 `createQueryCache` 只在后续读取或显式清理时移除过期值，关闭页面后可能长期保留最后一批已过期结果。现在缓存非空时每 30 秒做一次纯内存清理，过期后至多额外保留约一个清理周期（事件循环繁忙时会延后），不执行 SQL、不清除仍有效的 stale 数据，也不移除正在运行的加载。空缓存停表，定时器 unref，后续使用重新启动。
- **Agent SSE 聚合预算**：保留原单连接 16 帧 / 1 MiB 及 30 秒排空超时，额外限制进程所有连接的待发队列累计不超过 32 MiB 编码字节。到限时只关闭本次无法排队的控制连接，沿用既有重连机制，不操作转发进程。排空、错误、断开、替换连接均归还预算。预算仅指应用待发队列，不是进程总内存或 socket 总缓冲上限。

### 追加对比

基线是上述数据库驱动/IP 库优化已经完成、但本节改动尚未实施时保存的构建产物，不是再次与发布版混算收益。继续使用 Windows / Node 22.23.1，生产式打包的隔离测试入口，30 台假主机、10 条禁用规则及同一组 SQLite 数据；额外导入完整面板启动会注册的账单导出路由。邮件、Telegram、Cap、Excel 功能均未调用，无实际 Agent 或外网请求。

每组启动 3 个独立进程，分别采集初始化后、完成 36 次真实 HTTP/JWT/tRPC 首页/主机/规则请求后的内存，快照前均进行诊断 GC。三次中位数：

| 指标（MiB） | 本节优化前 | 本节优化后 |
| --- | ---: | ---: |
| 初始化后 heapUsed | 46.72 | 36.03 |
| 初始化后 RSS | 189.92 | 186.93 |
| 日常页面查询后 heapUsed | 48.77 | 38.09 |
| 日常页面查询后 RSS | 192.83 | 189.32 |

另外给一个独立展示缓存注入 8 MiB 合成二进制值，用虚拟时钟推进到过期后的清理周期；优化前数据仍驻留，优化后经诊断 GC，进程 ArrayBuffer 从 8.17 MiB 回到 0.17 MiB。该数据仅验证缓存生命周期，不代表真实面板每次会固定节省 8 MiB，且不与基线 RSS 重复相加。
