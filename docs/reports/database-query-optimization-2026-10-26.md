# 数据库查询优化验证（2026-10-26）

## 改动与边界

- MySQL / PostgreSQL 最新主机指标不再对保留期内全部样本做窗口排名，改为使用现有索引按主机取最新两条；100 台主机一批，保持同时间戳按 ID 排序及速率差分算法。SQLite 原本已有该策略。
- 用户权限读取只取有效订阅的资源 ID，保留快照、无快照旧套餐回退、到期和取消检查；不顺带查询附加流量、价格，也不缓存鉴权结果。
- 套餐完整展示批量读取资源和附加流量，不再按订阅逐份查询；购买、赠送、过期及取消的统计语义保持不变。
- 已授权主机和隧道在 SQL 内按 ID 筛选，不读取整张资源表再过滤。主机选项的旧 schema 兼容分支也在 SQL 内限制用户范围。
- 设置每批最多 200 项合并 UPSERT；按键批量读取保持实时，不使用全部设置的短缓存替代安全判定。
- 规则流量汇总明确关闭延迟查询，不为数量/流量读取延迟历史；主机分组数量用 SQL 聚合，而不是加载所有成员。

没有新增 Redis 依赖，没有扩大连接池，没有压缩历史保留期或删除业务数据。累计流量使用原有计数表；时间区间统计继续保留桶、历史修正及兼容回退。转发链的逻辑规则归并不能简单替换为子规则相加，否则会重复统计，因此保留原有算法。

## 远程环境与隔离

使用授权测试 VPS：Debian 13，2 核、约 1,974 MiB 内存。现有 aaPanel、MySQL 5.7、Agent 不改配置、不连接其数据库。测试数据库独立运行于 Docker 私有网络，不发布端口，也没有启动通知、探测或转发任务。

- Node 22.23.4：1 核 / 512 MiB 限额。
- MySQL 8.0.46：0.5 核 / 768 MiB，InnoDB 缓存 128 MiB，`max_connections=64`。
- PostgreSQL 16.15：0.5 核 / 384 MiB，`shared_buffers=64MB`，`max_connections=64`。
- 两种数据库顺序测试，不同时运行；面板运行时使用原有连接池策略。

初次测试脚本误把 MySQL 初始化期间的 Unix socket 就绪视为 TCP 就绪，首次连接得到 ECONNREFUSED；该轮未开始播种和测量，不计入结果。改为等待 TCP 就绪后，使用全新隔离目录重测。最终两种数据库均无 OOM，所有结果断言通过。

## 假数据与方法

每种数据库独立播种：200 个用户、1,000 台主机、500 条隧道、2,000 份订阅、4,000 条附加流量记录、200,000 条主机指标。被测用户有 10 份有效订阅，混合快照与无快照旧数据；50 台有指标的主机各保留 4,000 条样本。

基线为 `7a6f1cb`；优化版为本次工作区的指标、权限、套餐和设置代码。每种数据库按 **基线 → 优化 → 优化 → 基线** 顺序跑四轮，每轮每场景预热两次、测量 12 次。并发场景另设 8 个调用者各执行 8 次，总计 64 次。直接调用真实 Repository 和数据库驱动，不经过展示缓存，用断言检查数量、速率、权限集合和附加流量结果。

这是数据库路径对照，不是浏览器端到端压测，也不是可承载用户数的证明；未测长时间稳定性、真实 Agent 写入竞争或实际支付。每轮样本较少，CPU 限额会使尾延迟波动；下表报告两轮 P50 的范围，不把单项提速换算为全站性能倍数。

## SQL 次数与返回行数

两种外部数据库的次数相同，按单次逻辑调用计算：

| 场景 | 基线 SQL | 优化 SQL | 基线 / 优化返回行数 |
| --- | ---: | ---: | ---: |
| 9 台主机最新指标 | 1 | 1 | 18 / 18 |
| 50 台主机最新指标 | 1 | 1 | 100 / 100 |
| 10 份订阅完整信息 | 36 | 6 | 45 / 45 |
| 授权主机列表 | 38 | 4 | 1,046 / 27 |
| 授权隧道列表 | 40 | 6 | 547 / 28 |
| 保存 50 项设置 | 50 | 1 | 无结果行 |

返回行数包含权限、订阅等辅助 SQL，不只是最终返回给调用者的数组。指标查询 SQL 数量及返回行数不变，主要收益是数据库内部无需扫描和排名全部历史。

## 实测耗时

单位为毫秒，两轮 P50 范围，四舍五入：

| 场景 | MySQL 基线 → 优化 | PostgreSQL 基线 → 优化 |
| --- | --- | --- |
| 9 台主机最新指标 | 215–227 → 8.7–9.5 | 65–80 → 3.4–3.8 |
| 50 台主机最新指标 | 1,479–1,511 → 93–94 | 295–405 → 16–17 |
| 10 份订阅完整信息 | 28–29 → 7.5–9.1 | 21–22 → 6.7–6.9 |
| 授权主机列表 | 81–91 → 5.7–6.2 | 57–59 → 5.2–6.1 |
| 授权隧道列表 | 42–44 → 6.3–6.9 | 32–38 → 6.9–8.3 |
| 保存 50 项设置 | 21–22 → 1.6–2.0 | 16–18 → 1.3–1.9 |

8 并发的 9 主机指标场景，总计 64 次调用：MySQL 总耗时约 16.4–19.5 秒降到 1.16–1.18 秒；PostgreSQL 约 3.32–3.45 秒降到 0.37–0.38 秒。此结果只代表对应查询路径。原始本地记录位于忽略目录 `dist/load-test/database-audit-2026-10-26/`。

## 本地回归

`server/databaseReadOptimizations.test.ts` 校验：快照和旧数据回退、跨用户隔离、实时取消订阅、购买/赠送分开汇总、排除过期和取消、返回对象不共享可变附加流量数据、450 项设置仅三条 SQL、缓存失效、数量聚合、流量汇总不查询延迟历史及兼容查询的 SQL 范围。

运行 `pnpm test:performance`、服务端回归、TypeScript 检查及生产构建。SQLite 采用真实临时数据库测试，未将 Windows 本地耗时与 VPS 的外部数据库耗时混合比较。

## 清理

结果取回后，删除测试容器、网络、下载的三种 Docker 镜像、临时数据库与测试目录（含自动生成的测试凭据）。原有服务和数据不改动；本轮没有推送、发布或增加版本号。
