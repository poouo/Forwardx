# 主机瞬时速率与迁移健康检查修复验证（2026-11-19）

## 速率断档的故障路径

对比 v2.3.295、v2.3.296 和当前实现：早期界面主要用最近两条累计网卡计数相减，没有严格限制旧样本的展示；当前统一计算增加了 90 秒过期保护。过期保护能避免历史速率一直冒充实时，但也暴露了采集与配置核对耦合的问题。

普通完整心跳在配置核对并发闸门繁忙时可能提前返回，原实现会跳过网卡指标接收。独立在线心跳虽然保持主机在线，却没有网卡计数；完整心跳本地扫描或请求阻塞时，也无法补上样本。因此可以出现主机在线、速率连续几分钟缺失。这里复现并修复了这条故障路径，尚无用户生产日志证明它是所有反馈的唯一原因。

修复包括：

- 普通心跳在进入配置核对闸门前接收已认证网卡样本，合并请求不再丢失该样本。
- 查看实时指标期间，独立在线心跳携带 `/proc/net/dev` 和 uptime 的轻量数据，不等待完整心跳请求锁，不执行完整系统扫描。
- 服务端以 Agent uptime 计算采样间隔，以接收时间判断新鲜度；使用有界内存缓存，处理迟到、重复、重启和计数回退。
- 卡片和即时汇总采用独立网卡样本时间；完整 CPU、磁盘指标与历史曲线仍保持原记录及时间配对。
- 保留 90 秒过期保护。真正断开采样不能继续显示旧速率；有效零流量显示 0，离线或无法计算时保持暂无数据。

新功能需要面板与 Agent 配套升级。实时缓存不代替数据库历史记录，面板重启后需要重新形成两个有效网卡样本。

## GitHub #24：SQLite 迁移健康检查误报

[原议题](https://github.com/poouo/Forwardx/issues/24) 描述无缝迁移只读阶段，健康检查获取 SQLite 独占连接锁时被写入保护拦截，进而误判数据库不可用。

固定的 `SELECT 1` 健康检查改为在迁移内部上下文获取原有连接锁，不放开业务写入或任意独占操作。新面板 verifying 阶段的提示改为新面板正在验证，避免误写成旧面板。数据库真正不可用时，只读迁移状态接口仍可诊断，迁移写接口继续返回不可用。

真实 SQLite 回归覆盖源面板 frozen / forwarding / archived、新面板 verifying；健康检查通过，业务及任意 EXCLUSIVE 写入仍拒绝；关闭实际连接仍按原故障确认逻辑判定不可用。
