# 迁移到新面板

迁移是把数据搬到另一台面板，和原地升级不是一回事。操作前先备份两端数据库；迁移不会删除旧面板的数据。

| | 无缝模式（默认） | 普通模式 |
| --- | --- | --- |
| Agent 的面板地址 | 不变，由旧面板转交请求 | 切换到新面板 |
| 转发进程 | 不重启 | 可能重建，已有连接可能中断 |
| 旧面板 | 必须一直保留运行 | 新面板稳定后可以停掉 |

## 无缝模式（默认选择）

管理和计费迁到新面板，Agent / FXP 继续使用原来的面板地址，由旧面板把加密请求、SSE、流量报告和支付回调转交给新面板。迁移过程不会下发停止、升级或重建转发进程的指令，已有的业务连接不会被主动断开。

### 前提

- 两端面板版本相同、数据库类型相同，都是单实例，迁移期间没有其他面板实例或外部程序写入数据库。
- 所有主机的 Agent 不低于当前版本。
- 新面板没有业务数据（可以有一个初始化管理员）。
- 旧面板已配置正确的公开地址，迁移时填写的旧地址要和 Agent 正在使用的面板地址一致。

### 步骤

1. 备份两端数据库，配好新面板的公开地址。不要修改 Agent 的面板地址，也不要重启转发进程。
2. 在旧面板生成迁移码；在新面板的初始化向导或系统设置里开启“无缝迁移（旧地址转交）”，填写新旧地址和迁移码。
3. 旧面板管理员核对地址和模式后批准。旧面板随即暂停新操作、后台任务和计费写入，等进行中的操作结束后导出快照。这期间转发照常，Agent 和支付回调会短暂收到可重试的错误。
4. 新面板在一个事务里导入并校验行数，保留原来的 ID、Token、端口、累计计费和运行状态。导入成功后旧面板开始转交请求；新面板先只接收上报，核对原来在线的主机和运行中的规则、隧道，暂不下发配置变更。
5. 核对通过后新面板恢复正常管理。旧数据库保留，但不再写入。

### 迁移之后

- 新面板的初始化管理员会被旧面板的账号替换，需要重新登录；浏览器 Cookie 和 JWT 密钥不迁移。
- 新面板自己的数据库连接和 SSL 配置保持不变，不会被旧面板的证书覆盖。以文件路径配置的证书、外部文件和反向代理配置要提前在新机器上准备好。
- **旧面板的接入地址和转交服务必须一直保留，不能停止或卸载旧面板。** 所有管理操作在新面板进行。这种方式不支持增量合并；要彻底撤掉旧服务器，需要另外把旧域名或接入网关迁走，并确认接入地址和认证不变。
- 迁移状态保存在数据库配置目录旁的 `seamless-migration.json`（可用 `FORWARDX_SEAMLESS_MIGRATION_STATE_PATH` 指定路径），要和配置一起持久化。文件里有接管凭据，不要公开、删除或复制到其他部署。

### 取消和失败处理

- 旧面板已冻结但还没开始转交时，可以用仍然有效的管理员会话取消并恢复旧面板。开始转交后不能取消，只能在新面板继续完成验证，否则两端会同时计费。
- 接管前导入失败会整体回滚。旧面板的冻结最多保持一小时，超时自动解除；此时旧快照作废，需要备份后重新准备一个空的新面板再迁移。
- 接管请求发出后遇到网络错误，新面板会停在验证状态，管理员登录后点“继续验证并接管”。旧数据库不会自动恢复写入。

迁移的验证只核对数据和本地运行状态。建议迁移时保持一条真实的业务长连接，并确认转发进程的 PID 没有变化。

## 普通模式（关闭无缝开关）

先把新旧面板升级到同一个支持迁移的版本，并确认旧面板上在线的 Agent 心跳正常。

1. 在旧面板的系统设置中生成迁移码。
2. 在新面板初始化向导或系统设置中填写旧面板地址、迁移码和新面板访问地址。
3. 回到旧面板，核对目标地址后批准迁移请求。
4. 等待新面板完成数据校验、公开地址验证、Agent 预切换和原运行规则恢复检查。
5. 页面显示迁移完成后，使用旧面板账号登录新面板检查业务。

普通模式会把 Agent 的面板地址切到新面板，可能重建转发运行时，已有连接可能中断。只有在新面板地址确实指向当前面板、原来在线的 Agent 已经回连、迁移前运行的规则和隧道都重新运行之后，旧面板才停止控制 Agent；提交接管前检查失败会取消切换。

确认新面板稳定后，可以手动停掉旧面板。旧面板的数据库和业务记录不会被自动删除。
