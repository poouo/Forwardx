# 流量与延迟

流量、连通性和探测质量是不同指标。规则“运行中”、TCP 可连接或图表没有丢包，都不保证应用协议握手和真实业务正常。

## 流量口径

| 数据 | 含义 |
| --- | --- |
| 规则流量 | 规则统计点上报的入向 / 出向累计值 |
| 主机流量 | 主机配置网卡的流量，与规则汇总不是同一指标 |
| 用户用量 | 按用户授权、套餐或按量计费配置统计的用量 |
| 单规则限额用量 | 规则设置额度后相对基线的使用量，随逻辑规则保留 |
| 实时速率 | 单位时间吞吐，不是累计额度消耗 |

主机网卡还可能包含 SSH、面板、探测、其他程序与隧道承载流量，不应要求它与业务规则流量完全相等。切换网卡、重置周期、倍率和统计范围也会影响对比。

### 计量方式

设当前统计范围内入向累计为 `in`、出向累计为 `out`：

| 方式 | 用量 |
| --- | --- |
| 仅出向 | `out` |
| 双向合计 | `in + out` |
| 取最大值 | `max(in, out)` |

“取最大值”取该范围内两方向累计值中的较大者，不是每个采样点分别取最大再相加。先核对主机 / 用户 / 规则、统计周期、倍率及是否重置，再比较数字。管理员单规则额度从设置时建立基线，不等于规则卡片的全部历史流量，见 [规则限额](./rules.md#单条规则限额与有效期)。

### 流量不增长

1. 用真实客户端发起业务，确认规则的入口和最终目标正确。
2. 检查 Agent 上报时间及规则运行状态，区分主机网卡用量与规则用量。
3. 查看对应工具的统计来源；用户态运行时统计与 iptables / nftables 计数并非全部采用相同路径。
4. 检查日志中的计数器读取、上报、规则应用或数据库错误，不要先清空防火墙规则。
5. 保留规则 ID、主机 ID、工具类型、面板 / Agent 版本、异常时间及 [相关日志](./paths-logs.md)。

## 延迟与失败率

| 探测 | 测量内容 | 失败率代表什么 |
| --- | --- | --- |
| Ping | Agent 到配置目标的 ICMP 往返时间 | Ping 丢包率 |
| TCP | 到指定端口建立 TCP 连接的耗时 | TCP 连接失败率，不是网络层丢包率 |
| 链路分段 | 相邻节点或最终目标的探测结果 | 对应段的探测失败率，不是全链路业务丢包 |

TCP 连接成功不表示 Snell、AnyTLS、TLS 等协议握手通过，也不能证明同端口 UDP 正常。Ping 可能被限速或禁止，而业务连接仍然可用。

### 图表下方的统计

统计区显示次数、最大 / 最小 / 平均延迟、失败率与稳定性。支持累计计数的 Agent 上报探测总次数和成功次数，面板通过递增差值统计，避免只保存异常或抽样成功记录造成失败率失真。

- 失败率按 `失败次数 / 总次数 × 100%` 计算，不根据延迟曲线上的点数估计。
- 统计只覆盖支持计数的 Agent 自首次可观察上报后的数据；不补算旧记录，边界精度受上报间隔影响。
- 缺少可靠累计计数时显示暂无数据或 `--`，不把未知当作 0%。
- 0% 表示当前可观察样本没有失败，不意味着网络永远不丢包。
- 稳定性是探测参考分，不是运营商 SLA；同时查看样本数、最后上报时间与统计口径。

削峰 / 平滑只影响曲线展示，不改原始数据、探测失败计数或计费用量。长时间窗口可能合并图表点，因此曲线点数与探测次数不必相等。

## 多跳与自测

在规则或链路详情执行自测，按入口 → 中转 → 出口 → 目标逐段查看。入口组、备用中转和多出口是可选分支，不应把所有替代路径都当作串行必经节点；某分支失败不一定代表整条链路不可用。

手动自测会发起新的探测，正常探测刷新不应清空已就绪运行状态或重建业务。若资源正在应用或恢复，测试可能等待就绪；超时、下发失败与目标不可达会分别提示，不能用旧的成功记录证明此次通过。

分段延迟用于定位，不要将分段之和视为真实客户端完整握手耗时。测试通过后仍需用真实业务验证。

## 公开主机监控

独立监控地址默认是 `/dev`，可由管理员配置。页面按可见状态刷新，网络恢复或返回前台时恢复请求；暂时失败会保留上次数据并显示刷新时间，可手动重试。先核对时间戳，不要把保留的旧图表误认为新探测。

Agent 离线时没有新的有效探测。历史曲线仍可查看，缺测区间不应解释成 0 ms 或 0% 丢包。
